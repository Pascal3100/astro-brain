### Session 37 — OTA bootstrappé + JALON C VALIDÉ : la monture est pilotée par INDI (2026-07-05)

Thread matériel → **logiciel**. L'ESP32 répond et entend (S36) → on ferme la boucle : flash OTA opérationnel, puis on branche le vrai driver INDI sur la monture. Skill `systematic-debugging` (contradiction « l'encodeur bouge mais rien ne bouge » élucidée).

**(0) Bootstrap OTA — fait et vérifié.** Le firmware `firmware/esp32-aux-bridge` contient déjà l'OTA en source (jamais flashé, S36). Dernier flash USB de bootstrap : `arduino-cli compile --upload -p /dev/ttyUSB0 --fqbn esp32:esp32:esp32` (970 Ko, hash vérifié), power-cycle sur le bench → WiFi `.200`. **Double vérif** : round-trip bus **10/10** (fix turnaround S36 conservé) + sonde UDP 3232 → **`AUTH <nonce>`** = ArduinoOTA écoute et attend le mot de passe. ⇒ flash par WiFi désormais opérationnel (`espota.py -i 192.168.1.200 -p 3232 -a astrobrain -f <bin>`), plus jamais de débranchage. Sonde `aux_probe.py` (round-trip GET_VER azimut via TCP 2000) recréée au scratchpad (l'ancienne, session-specific, avait disparu).

**(1) Jalon C — le driver dialogue avec la vraie monture.** État découvert : `indiserver.service` (systemd, port 7624) + `astro-brain.service` déjà actifs ; le driver `indi_celestron_aux` **déjà configuré en mode Network** (`CONNECTION_MODE.CONNECTION_TCP=On`, `DEVICE_ADDRESS=192.168.1.200:2000`) mais **déconnecté**. `indi_setprop "…CONNECTION.CONNECT=On"` → **`CONNECTION._STATE=Ok`** : handshake réussi à travers le pont. Le driver poll les positions (RA/DEC/AZ/ALT) ; au repos AZ **rock-stable** (3 lectures identiques) = vrai encodeur, pas de simulation.

**Débogage de la contradiction « ça ne bouge pas ».** 1er slew (rate 5x, 2 s) → AZ `360.000 → 0.093°`, utilisateur : rien vu, rien entendu. Phase 1 systematic-debugging (refus de deviner) : (a) lecture au repos = stable → encodeur réel ; (b) le `360.000` initial est la **position par défaut** avant le 1er poll, le `0.093` la **1ʳᵉ vraie lecture** → ce « delta » n'était **pas** un mouvement. Reproduction propre à **rate 8x** : AZ `0.333 → 2.474 → 4.403°` pendant 3 s puis figé → **mouvement réel ~2°/s**, et l'utilisateur **confirme visuellement** (« là ça a bougé »). Contradiction levée : le hardware et le protocole marchent, le 1er essai était l'artefact de démarrage (à 5x le pas était aussi moins perceptible). ⚠️ La vitesse **9x n'existe pas** dans `TELESCOPE_SLEW_RATE` (1x→8x seulement).

**⇒ Macro 1 débloquée.** La chaîne complète `Driver INDI → TCP → pont ESP32 → interface 74AHCT125 (TX) / LM2902 (RX) → bus AUX → moteur` pilote la vraie monture (connexion + lecture encodeur + slew bidirectionnel). Le blocage qui datait de S26 (~10 sessions) tombe. Tout le software Macro 2/3 déjà écrit devient validable contre du hardware réel.

**(2) Test end-to-end REST → bug backend trouvé et corrigé (TDD).** Le « flapping » du log `indiserver` (`Client N: broken pipe/read EOF` ~2 s) était une **fausse alerte** : c'étaient **mes propres `indi_getprop`/`indi_setprop`** (chaque CLI ouvre/ferme une connexion) ; le backend tient en réalité **une** connexion stable (`ss` : uvicorn ↔ 7624 `ESTAB`), log vide au repos. En revanche, `POST /slew` renvoyait `{"ok":true}` **sans que la monture bouge**. Débogage (`systematic-debugging`) → **cause racine unifiée** : le `MountIndiAdapter` accédait aux éléments INDI d'une façon que seul le `FakeIndiClient` (trop permissif) acceptait. Introspection live du vrai `pyindi-client` → **3 pièces** : (a) **accès** `vec["NOM"]` lève `TypeError` sur le réel (index int only) → il faut `findWidgetByName` ; (b) **état switch** `setState("ON")` est silencieusement ignoré (reste Off) → il faut l'entier `ISS_ON=1` + lecture `getStateAsString()=="On"` ; (c) **noms** rate = `1x`…`8x` (pas `SLEW_RATE_n`), abort = `ABORT` (pas `ABORT_MOTION`). Le même bug d'accès sur `time_vec["UTC"]` **était le `TypeError` `set_time`/`set_location` de S27** — corrigé au passage. **Fix TDD** (`test-driven-development`) : fake rendu **fidèle** au vrai pyindi (le RED reproduit les 3 bugs → 23 échecs), puis fix de tous les sites (`_indi_property_helpers.find_widget` + `SWITCH_ON/OFF`, slew/stop/abort/time/location/sync/goto/cordwrap/backlash) → **343 tests verts**, lint OK. Bug « `{"ok":true}` trompeur » jugé acceptable : l'échec **remonte via SSE `/state`** (`mount:error`), contrat POST-accepté + état-par-flux défendable.

**Second bug (préexistant) démasqué au déploiement : device pyindi périmé.** Après déploiement, le slew REST échouait encore (`KeyError '8x'` / `'ABORT'`, message `No ISwitch … in .` — **device vide**). Introspection décisive : un handle `getDevice` **caché trop tôt** (dès qu'il est non-None, avant que le driver ait défini ses propriétés) est **périmé** → device caché tôt = 16 éléments nommés `""` ; `getDevice` **frais** = 8 éléments `1x`…`8x`. Fix : `MountIndiAdapter._device` devient une **propriété re-fetchée à chaque accès** (jamais cachée), gardée par `_connected` (posé dans `start`, levé dans `stop`) ; test TDD empty-then-full → **344 verts**.

**✅ END-TO-END VALIDÉ SUR MATÉRIEL RÉEL.** Après ce 2ᵉ fix (commit + push + `git pull` Pi + restart), `POST /slew {az,+,8}` → **la monture tourne** (AZ 9,285° → 11,341° en 2 s, figée à l'arrêt, `mount:ready`). La chaîne `app-path REST → FastAPI → pyindi-client → indiserver → pont ESP32 → bus AUX → moteur` est **prouvée de bout en bout**. **Macro 1 bouclée.**

**🔜 Reprise :** (1) refermer la passe physique mount-branchée Macro 0 (`INTEGRATION_CHECKLIST.md`) ; (2) rouvrir la Macro 2 Setup (backlash mount-side, désormais débloqué) ; (3) valider le wizard 3 étoiles + GoTo réel contre le matériel (même path adapter, désormais corrigé) ; (4) fix firmware auto-restart WiFi RTC (identifié S32, pas flashé).

### Session 36 — Turnaround TX→RX résolu : round-trip AUX 30/30 (100 %) (2026-07-02)

Thread matériel + firmware (suite S35). Édition workstation, **flash ESP32 en USB** (`arduino-cli`, `/dev/ttyUSB0`, FQBN `esp32:esp32:esp32`), tests **par sonde TCP** sur `192.168.1.200:2000`. Skill `systematic-debugging`. Point de reprise S35 (« corriger le turnaround ») **fermé**.

**Problème de provenance d'abord.** Le firmware qui a fait répondre le moteur en S35 (pilotage `/OE` GPIO32) **n'avait jamais été committé** — le fichier du repo était la version S33 (commentaires BC547/4093, aucun `/OE`). Source S35 **perdue** (même schéma que le rapport deep-research S30). Décision : **reconstruire** proprement dans le repo à partir du câblage doc (`GPIO17→1A`, `GPIO32→/OE` actif bas, `1Y→470Ω→DATA`, LM2902→GPIO16) + schéma de réf g7ltt/Mark Lord.

**Diagnostic rigoureux (dump brut avant tout fix).** Reconstruction initiale : round-trip **0/10** mais signature ultra-nette — réponse toujours 7 octets `[XX] 10 0d fe 05 09 d2` (XX∈{05,00,15,2a}), **le préambule `3b` systématiquement perdu**, le reste parfait. Deux causes possibles (glitch de framing vs drain d'écho fautif) → **refus de deviner, instrumentation** : `ECHO_SUPPRESS=0` (relaie tout) + sonde en mode dump brut. Résultat décisif : **écho = 6 octets propres** (`3b 03 0d 10 fe e2`) **et** le `3b` de la réponse **absent dès le flux brut** → drain/comptage **innocentés**, c'est un problème de framing au retournement.

**Cause racine : collision de bus.** Ma séquence d'émission gardait `/OE` LOW (74AHCT125 pilote HIGH) pendant **573 µs de plus** après `Serial2.flush()` (une garde `delayMicroseconds` « pour les stop bits »). Or le moteur a reçu notre dernier octet **dès le flush** et commence à répondre dans cette fenêtre → nous tenons la ligne HIGH pendant qu'il tire son start-bit LOW → **contention** qui détruit le 1ᵉʳ octet `3b` et bave le `05`, puis dès qu'on relâche il pilote seul (reste propre).

**Fix (une variable).** Retirer la garde : **`/OE` HIGH immédiatement après `flush()`** (le `flush()` garantit déjà la fin de transmission, shift register vidé — l'écho 6/6 propre le prouve). Vérifié en 3 temps : (1) fix + `ECHO_SUPPRESS=0` → brut **8/8** avec `3b` (`3b 05 10 0d fe 05 09 d2`) ; (2) `ECHO_SUPPRESS=1` prod → **12/12** puis **30/30** réponses valides (en-tête + checksum recalculé OK). **Bus AUX fiable de bout en bout** — le hardware S35 (74AHCT125 TX + LM2902 RX) est confirmé, le ~1/3 est mort.

**Ops :** utilisateur désormais **dans le groupe `dialout`** → plus de `sudo chmod` sur `/dev/ttyUSB0` (note S33 caduque). Cycle de flash : conflit 5 V → USB workstation pour flasher, bench pour tester ; le passage bench→USB→bench fait un power-cycle propre (l'ouverture du port par arduino-cli laisse parfois l'ESP32 figé par DTR/RTS — un reboot le lève). Sonde `aux_probe.py` (validante) + `aux_probe_raw.py` (dump brut) dans le scratchpad.

**OTA bootstrappé et vérifié (2026-07-05).** `ArduinoOTA` intégré au firmware (hostname `astro-brain-aux`, port 3232, mot de passe `astrobrain`) pour flasher **par WiFi** et ne plus subir le cycle USB↔bench (conflit 5 V). Le **flash USB de bootstrap est fait** : build+upload `arduino-cli` sur `/dev/ttyUSB0` (970 Ko, hash vérifié), l'ESP32 reprend le WiFi `.200` au power-cycle bench. **Double vérif post-flash** : round-trip bus **10/10** (fix turnaround S36 conservé) **+** sonde OTA UDP 3232 → réponse **`AUTH <nonce>`** = OTA actif et protégé. ⇒ à partir de maintenant, flash par WiFi opérationnel : `espota.py -i 192.168.1.200 -p 3232 -a astrobrain -f <bin>` (`~/.arduino15/packages/esp32/hardware/esp32/3.3.10/tools/`), plus jamais de débranchage. Sonde de vérif `aux_probe.py` (round-trip GET_VER azimut via TCP 2000) recréée au scratchpad.

**🔜 Reprise prochaine session (ordonnée) :** ~~(0) bootstrap OTA~~ **fait (2026-07-05)** — OTA flashé + vérifié (`AUTH`), flash WiFi opérationnel ; (1) **jalon C INDI** : `indiserver -v indi_celestron_aux` en mode Network (`.200:2000`) sur le Pi, voir si le driver dialogue (GET_VER, positions, slew réel) ; (2) **ADR pivot ESP32** (déroge à « pas d'Arduino ») ; (3) fix backend `set_time`/`set_location` (S27).

### Session 35 — Hardware AUX validé : le moteur répond (round-trip TX) (2026-07-01)

Thread matériel (suite S33/S34). Câblage du **74AHCT125** sur l'établi, tests **depuis le Pi** (`ssh astro-brain`, sonde `GET_VER` en TCP sur `192.168.1.200:2000`). Le point 🔬 « à valider » de S34 est **tranché positif**.

**🟢 Le round-trip TX passe — première réponse moteur depuis S26.** TX migré du **BC547 open-collector** (fronts montants trop lents, moteur muet S33) au **74AHCT125** buffer tri-state (drive **actif push-pull** HIGH+LOW, 470 Ω série, `/OE` piloté par GPIO32). LM2902 conservé en RX (oreilles, prouvé S33). Sonde `GET_VER` (`3b 03 0d 10 fe e2`) vers l'azimut → le contrôleur répond **`3b 05 10 0d fe 05 09 d2`** : src `0x10` (moteur), dst `0x0d`, cmd `fe`, données `05 09` = **firmware v5.09**, checksum `d2` valide. ⇒ **le blocage électrique S26→S33 (drive physique insuffisant) est levé** ; le pivot 74AHCT125 acté en doc S34 est confirmé au banc. La monture est bien alimentée (elle répond).

**Bémol — fiabilité ~1/3.** Sur 3 essais consécutifs, la réponse moteur n'arrive propre qu'une fois ; les 2 autres, l'**en-tête** de la trame réponse (`3b 05 10 0d fe`) est écrasé en un octet poubelle (`e4`/`ce`), seule la queue `05 09 d2` survit. Mon écho, lui, repart toujours propre (`3b 03 0d 10 fe e2`). Signature du **retournement half-duplex TX→RX** : juste après avoir cessé d'émettre, l'ESP32 n'est pas encore prêt à recevoir et perd le début de la réponse qui arrive dans la foulée. C'est du **timing firmware** (fenêtre `/OE`, purge/réarmement RX après émission), **pas** un défaut de câblage — le hardware est validé. ALT `0x11` reste muet au GET_VER (normal SLT). ⚠️ L'ESP32 porte toujours le **build diagnostic** (`ECHO_SUPPRESS 0`, d'où l'écho visible) → à reflasher normal.

**Doc :** `cablage-interface-aux.html` — schéma **vue composants** du 74AHCT125 ajouté (boîtier DIP-14 vu de dessus, pattes numérotées, R 470 Ω + C 100 nF dessinés, fils tracés vers rails / GPIO / DATA), en remplacement du schéma symbolique jugé illisible.

**🔜 Reprise prochaine session (ordonnée) :** (1) **corriger le turnaround TX→RX** côté firmware (délai avant Hi-Z `/OE` + vidage du buffer RX après émission) → viser un round-trip fiable ; (2) reflasher `ECHO_SUPPRESS 1` (normal) ; (3) **jalon C INDI** : `indiserver -v indi_celestron_aux` en mode Network (`.200:2000`), voir si le driver encaisse le résiduel (retries) ; (4) **ADR pivot ESP32** (déroge à « pas d'Arduino »).
